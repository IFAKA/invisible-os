# Invisible OS

Android app: control the phone with one earbud button, screen off. The phone speaks the options; one click picks.

## Rules
- **No microphone. Ever.** Do not request RECORD_AUDIO, do not use SpeechRecognizer, do not add voice input or dictation. Input is only the button (click counts, hold) and, for text, the app screen or Share. Reason: the owner does not want the app to listen.
- Menu is English (it changes only when the owner picks another language); message text is read in its own language (English default; Spanish only when detected clearly).
- **The phone is on Wi-Fi debugging** (no cable). Run `adb devices`: a line `adb-...-tls-connect... device` means it is connected. Do not ask the owner to plug it in or turn debugging on; if it is missing, say so and ask them to turn Wireless debugging on. For a bug report ("it jumps"), take the lease, read `adb logcat -d -s Invisible` and run `tools/e2e.py` yourself before asking questions.
- **The phone is shared.** `app/run.sh` checks the phone lease (`~/.claude/bin/phone take MIN WHY` / `release`) and that your tree has everything on master. Do not bypass it: a stale install removes other sessions' dev hooks.
- Checks (from `app/`, all three must pass): `./gradlew testDebugUnitTest --offline -q` (every module), `./gradlew checkVoiceKit --offline -q` (kit rules and module borders, every module), `./gradlew assembleDebug --offline -q`. Install on the phone: `app/run.sh`.
- **Laptop flow tests (no phone, about 10 s):** `cd app && ./gradlew :os:testDebugUnitTest --offline --tests '*Flow*'` runs the `tools/e2e.py` scenarios on the laptop in fake time with the real button timing (mapping table at the top of `FlowTest.kt`; Robolectric for the raw button path, the listener and the Rooms tool against a fake server). Run them after any change to the button, menu, speech flow or rooms. Only the phone can still check the real Bluetooth/media key path, the real TTS engine making sound, real permissions and other apps' notifications: keep `tools/e2e.py` for those.
- **End-to-end on the real phone:** after a change to the button, speech, the menu or call/chat reading, run the laptop Flow tests first (`cd app && ./gradlew :os:testDebugUnitTest --offline --tests '*Flow*'`). Run the phone `tools/e2e.py` (after `app/run.sh`) only for what only the phone can check (real button over Bluetooth, real voice sound, permissions, other apps' notifications) or before a release. About 1 minute, no human; `--only NAME`, `--list`; log `app/logs/e2e.log`. The voice is an instant debug stand-in by default and menu silences are scaled (button timing never is); wake_reads_home_menu, click_picks, voice_speed_applied and chat_arrival_spoken keep the real voice to prove the engine. A scenario with the same inputs as its last pass is skipped, so only changed scenarios re-run (`--all` or `NOCACHE=1` forces all). It needs the phone lease and uses debug hooks in `AiTestReceiver` (reset, show, state, press, fake call/chat). It never picks "Yes, call now", Answer or a real reply. Add a scenario when you add behaviour a person would hear.
- **Modules** (Gradle root `app/`; Kotlin packages stay `com.faka.invisible.*`, the module is the border): `:oskit` (Voice Kit `voicekit/`, Logic Kit `logickit/`, `Ui.kt`, and the contracts in `oskit/`: `Program`, `ProgramHost`, `ProgramEntry`, `NotificationModule`, `NotificationHost`; depends on nothing), `:os` (the app: menu, `Actions`, services, tree; the only module that sees all the others), `:programs:echo|guard|duel|write|compass` (one program each, depends ONLY on `:oskit`), `:adapters` (one file per outside app, depends ONLY on `:oskit`). `checkVoiceKit` and `KitRulesTest` fail if a program or adapter depends on or uses `:os`, another program or an adapter.

## Trace log
- The app writes one line per thing a person did or the phone answered to `files/trace/trace-YYYY-MM-DD.log` (7 days kept; code in `oskit/.../oskit/Trace.kt`). Line: `HH:mm:ss.SSS kind detail`; kinds: gesture, key, screen, say, pick, item, notif, music, media, wake, exit, program, error, slow. Crashes are written too.
- Read it: `tools/trace.py --since 10m [--grep TEXT] [--day YYYY-MM-DD] [--summary]` (pulls from the phone, copy in `app/logs/trace/`). `--summary` shows errors, slow steps, gestures per screen, likely wrong picks, picks that led nowhere, repeated speech. After any bug report, read it before asking questions.
- Wake speed: `wake` lines `t+Nms step` give the time of each wake step (gesture to `speakItem called`); `say first audio +Nms` follows. Rules: nothing slow on the main thread in a gesture (sounds start on the `tones` thread; `TtsSpeech.setVoice` is cached per language; `DeviceApps.installedNow/useNow` return the last answer and renew in a background thread, so a new app or launch shows one wake later; the home list is built in the 400 ms screen-tone gap, `ControllerMode.prebuilt`). Wake to first audio is about 450 ms, 400 of it the tone gap.
- Every new behaviour a person would notice logs through `Trace.ev(kind, detail)` (errors: `Trace.err`; timings: `Trace.time`). Spoken lines and buttons are already traced by the kit.

## Design kits (enforced by `KitRulesTest` and the build task `checkVoiceKit`)
- Screens use only the **UI Kit** (`Ui.kt`: `Ui` colors/radii and `Kit` parts) and the **Voice Kit** (`voicekit/`, see `voicekit/KIT.md`).
- Voice Kit = everything that speaks, plays a sound, reads the button or reads a list. It has atoms, molecules, engines, organisms and one door, `VoiceKit`.
- Every spoken line is a `Phrase`. Fixed sentences live only in `voicekit/atoms/Sentences.kt` (the OS) or, for a program, in its own `*Sentences.kt` (one `allow` line in the rules file). Text from users or the world is `Phrase.content(...)`.
- Outside the kit you must not: use TextToSpeech, AudioTrack, SoundPool, MediaPlayer, ToneGenerator, audio focus, MediaSession; make `Phrase(`/`Phrase.fixed`; pass a string to `say`/`speak`; keep your own list index or loop count; write HOLD_MS/GAP_MS by hand. The build fails with file:line. The rules are in `app/voicekit-rules.tsv`.
- No `Color.*`, raw `TextView`/`Button`/`GradientDrawable` outside `Ui.kt`. If a part is missing, add it to the kit first, then use it.
- Lists: use the kit `Scanner`. Sounds: `Earcons.kt` in the kit. Check the kit with `cd app && ./gradlew checkVoiceKit --offline -q`.

## Logic Kit (check before you write any helper)
- Shared logic has a registry: `app/oskit/src/main/java/com/faka/invisible/logickit/KIT.md`. It lists what exists (text, language, messages, notifications, tree, tasks, learning, AI) and where. Search it and `krn find` first; reuse or extend. Never write a second copy.
- New shared pure helpers go in `logickit/` with a unit test and a row in the registry. Copying lines a second time is the sign to move them there.
- Enforced for what a pattern can catch: rule ids `logic-*` in `app/voicekit-rules.tsv` (now: white-space cleaning must use `squash()`/`words()`). Add a rule when you remove a duplicate.

## The OS and its programs (how every new game or tool is built)
The app is a small OS with no screen. Android is the building; this app is a shop inside it that you walk through with your ears.
- **The OS owns:** the one button (clicks and holds), the home menu (`ControllerMode`, `LauncherSettings.HUB_ITEMS`), speech, the screen tones (`voicekit/atoms/Earcons.kt`), the close sound, and the Games section (`Screen.GAMES`).
- **A program** is a module under `app/programs/` that implements `Program` (`oskit/Program.kt`): the Duel in `programs/duel` (package `tell`), Echo in `programs/echo` (a rhythm-copy game, see GAME-ECHO.md), Guard in `programs/guard` (a beat-keeping gate game with a tutorial, see GAME-GUARD.md), Write and Sum in `programs/write` (the keyboard), the Compass in `programs/compass`. It owns only its own rules, sounds and fixed sentences. It gets the raw button while it runs (`Program` is a `RawButton`). It asks the OS for things only through `ProgramHost` (context, handler, prefs, speak, pause or resume music, log, waiting sound, `ended()`); extras go through a small port interface of its own that the OS implements (Write: `WriteServices`). It never plays an OS sound and never touches the menu. It depends ONLY on `:oskit`; the build checks this.
- **Programs by other people:** `sdk/GUIDE.md` (starter in `sdk/starter`, `sdk/new-program.sh NAME [--from PATH | --remove]`, `sdk/pack.sh`; the framework is published from `:oskit`).
- **To add a game:** a new module under `app/programs/<name>` (copy the build file of `programs/compass`, add it to `settings.gradle.kts` and to the dependencies of `:os`), a `Program` class, a `ProgramEntry("games:<name>", title) { MyProgram() }`, and ONE line in the registry `os/src/main/java/com/faka/invisible/Programs.kt`. The Games list, the start and the dev hook (`--es start <name>`) come from the registry. When the program ends it calls `host.ended()`; the OS plays the close sound. Do not copy that into the program.
- **To add a tool (not a game):** one key in `LauncherSettings.HUB_ITEMS`, a program module as above with id `hub:<key>` (one registry line; the hub `when` in `ControllerMode` finds it there), and one tag line `Group/Sub  hub:key` in `AppCategories.kt`. The tree places it by that tag; never put a tool in the Games list. `AppCategoriesTagsTest` fails if a program has no tag.
- **Notifications (the hotel mailbox):** the listener keeps every app's notifications (`NotificationStore`); private ones (secret, locked-private, bank or password apps) are read as "<App>, new notification" only. Home has ONE "Notifications, N" entry (only while a non-muted app has notifications; right after the live apps, so home has at most 11 entries, 12 with 3 live): it opens the apps that have notifications ("WhatsApp, 3 notifications"), "Clear all" first (clears every app, speaks "7 notifications cleared", goes home). An app with 2 or more notifications opens its list ("Clear all from this app" first); an app with exactly one skips the list and reads it in full, then its actions. This holds from the tree too. Triple click goes one level up (single notification or app list, then the Notifications list, then home; from the tree back to the tree). The rest of home is a tree of ALL apps and OS programs (`AppTree`, pure, searched for the lowest expected cost = items heard to reach an app, each level +0.5; groups named for what you want to do, from the table in `AppCategories`: Talk, Plan, Pay, Work, Watch and listen, Play, Go, Tools; the 8 groups are always direct entries of home (plus up to 2 promoted apps, home max 10), no other list over 8; an app is in its own group/sub-group or promoted to home, never lifted out of its sub-group into a mixed list (each list holds one kind of thing, so the name tells where to go); there is NO "More": a place has at most 8 entries, so split crowded places with finer tags; if an untagged pile still overflows it is cut by first letters, "A to D"; flattening and promotion chosen by cost). Order comes only from use: `AppWeights` = 1 (OS programs 3) + 3 * ln(1 + month launches + 2 * week launches) + 5 * own picks (launcher and system plumbing counts 0 launches), never minutes and never notifications (the owner does not watch them; unread only appears in a label, "WhatsApp, 2 notifications": a number always comes with what it counts). Launch counts come from `DeviceApps` (needs usage access, optional: the user turns it on from the setup checklist on the app's home screen, `Setup.kt`; no adb). `AppTreeTest` prints `REPORT` lines comparing the tree with a flat list (data `src/test/resources/app_usage.tsv` from `tools/usage_weights.py`). **Live apps first:** `LiveApps` (pure) picks up to 3 live apps (media playing, or paused in the last 10 min; or an ongoing notification with a chronometer, a media style or a category like transport, workout, stopwatch, navigation, call; static ongoing ones like USB debugging are not live), most recently updated first, and home puts them in front of the groups ("Music, playing", "Workout, 12:30 running"). Each live app takes one of the 2 promoted slots and is never promoted again (it stays in its group), so home has at most 10 entries, or 11 with 3 live. Picking one opens its notification with its actions (a music app opens the Music page). Walk home -> group -> app. An app with notifications opens its list, then one in full with its actions plus Dismiss, Mute this app, Open app; an app without opens "Open app" / "Back" (triple click goes up). The OS programs (Messages, Today, Tasks, Timer, Music, Phone, Games) are leaves of the same tree. The tree is rebuilt only when the home list is built (so picks move apps next time) and never changes while it is walked. To place a new app, add one line to the table in `AppCategories.kt`. A native module per outside app is one file in `app/adapters/` implementing `NotificationModule` (it asks the OS through `NotificationHost`) plus ONE line in `Adapters` in `Programs.kt`; the chat apps (`ChatAppsModule`) are the first.
- **Reset learning:** a tool (`hub:reset`, tag `Tools/Setup`). It walks Find (letter ranges, then the app; `resetting` in `ControllerMode`), "Everything" is the last item of the first list, then a confirm (the safe "No, go back" is read first). It forgets the picks of that app (`ChoiceLog.forget`) and saves the launch counts of that moment (`LearningReset`), so the tree uses only later launches.
- **Find:** a hold on the home list starts Find (`Screen.FIND`, `logickit/NameFinder.kt`): pick first-letter ranges (no favourites block: the tree already promotes your most used apps) ("A to C", then "C") until the app is read; a letter with up to 12 apps is read whole, most used first, and a bigger one is split by its first two letters ("Wa to We"), never "Other"; triple click = one step back. Everywhere else the hold is fast scroll.
- **First run:** the home screen is a numbered checklist (`Setup.kt`: Button access, Test your button, Notification access, Assistant, then optional Show notifications, Calendar, Location, Usage access), each with a plain reason and a button to the right Settings page or permission prompt. The first wake of the OS (a hold) runs the practice program (`programs/practice`, id `tutorial:practice`: click, two, three, click-then-hold, a sound after each) once (`practice_done` in prefs); the Help page replays it.
- **Fast scroll:** hold (one long press) steps through a list fast, first word + tick; release speaks that item in full. It is only active while a list is read (`ScanList`); everywhere else a plain hold does nothing. Click then hold (2nd press held) is exit, so exit is never an accident. Every list must be a `ScanList` (enforced by `KitRulesTest`).
- **No "Back" item in lists.** Triple click is Back everywhere (one rule in `ControllerMode`). Do not add a spoken Back option to a list.
- **Leaving:** hold 3 s always leaves a program. Click then hold closes the OS from anywhere, also inside a program (`ButtonInput` catches it before the program and calls `ButtonTarget.exitProgram`); a program must never give it another meaning, except Write (`RawButton.exitOnClickHold = false`): there a hold after a click picks the right word, and Write is left by holding 3 s. Say how to leave in its first minute. **Exception, Write:** its holds pick the right word (acts at 0.5 s while the button is still down; holding on does nothing more) and a click then a hold is normal typing, so Write has no hold-to-leave and no click-then-hold exit; it leaves from its menu (Letters, Delete, Phrases, Done, Leave).
- **Teaching (research: games for blind players):** teach by short play, not by speech; one mechanic at a time (the Duel has levels 1 to 3, then the full game); confirm every success with a sound; at most 7 words per spoken sentence; pauses follow `TellVoice.pauseAfter` (600 ms + 250 ms per word); keep few sounds at once; the same sound always means the same thing; the player sets the pace; narration can always be interrupted by a press.
- **Sounds are built on a background thread** (`TellSynth.warmAsync`); the phone is about 40 times slower than the laptop for synth work. Never build sounds on the main thread.
